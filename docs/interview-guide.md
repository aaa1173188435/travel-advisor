# 出行建议官 · 面试讲解手册

> 一句话：**输入「日期 + 城市 + 模式」，输出一份可解释、可执行的出行建议。**
> 它不是 prompt 套壳，核心是一个领域规则引擎；大模型只是可选的「润色层」，关掉也能完整运行。

---

## 1. 30 秒版本

我做了个出行建议服务：用户选日期、城市和场景（通勤 / 健身 / 旅游），它结合气候常年值、法定节假日与调休、节气、通勤高峰、旅游人流，给出一份带评分和分区建议的结果。天气可以接和风实时预报，大模型可以接 DeepSeek 润色，两者都是可选的——没网、没 Key 时自动退回纯规则，接口照常可用。前后端全栈，52 个测试，三种部署方式都跑通过。

## 2. 问题与目标用户

- **问题**：查天气的 App 只给温度，不给「所以我该怎么安排」；通用大模型给的建议不可核验，还会编造限行、票价、天气。
- **目标**：把「日期 + 城市 + 场景」翻译成**可执行、可解释**的建议，每条都能追溯到规则。
- **非目标**：不做实时导航、不做票务预订、不做长期气候预测。

### 分层职责

| 层 | 职责 | 关键文件 |
|---|---|---|
| 接入层 | 校验、限流、静态托管 | `app.py`、`schema.py` |
| 上下文层 | 把请求变成结构化事实 | `context.py` |
| 数据层 | 城市、节假日、节气、天气 | `cities.py`、`holidays.py`、`solar.py`、`weather.py`、`weather_api.py` |
| 领域层 | 每种场景怎么给建议 | `modes/commute.py`、`fitness.py`、`travel.py` |
| 编排层 | 缓存、降级、响应组装 | `engine.py`、`llm.py` |

## 4. 一次请求的完整链路

```
POST /api/advice
  { city: "白山", date: "2027-01-10", mode: "fitness",
    options: { activity: "run", duration: 45, intensity: "moderate" } }

1. 限流检查（Redis 无关，进程内滑动窗口）
2. Pydantic 校验（日期范围、城市非空）
3. 缓存命中？（相同输入 5 分钟内直接返回）
4. build_context：
   - 城市解析：中文 / 全拼 / 首字母 / 别称，未收录走通用兜底
   - 节假日：查 2026/2027 官方表；其它年份按固定日期估算并标 estimated
   - 节气：世纪常数公式近似（±1 天）
   - 天气：先查和风 7 天预报 → 3 天 → 失败/超窗回退气候插值
5. 取 mode=fitness，按「室内/户外」分支打分并生成 5 个分区
6. 若配置了 LLM：把事实 + 草稿交给模型，只允许改写结论（2—3 句、≤120 字）
7. 组装响应：headline / score / tags / sections / facts / warnings / meta
```

## 5. 关键设计决策（面试重点）

### ① 事实与语言分离：规则引擎优先，LLM 只做润色

**问题**：让大模型直接生成建议，会编造天气、限行、票价，且结果不可复现。

**选择**：规则引擎产出结构化事实和建议草稿，LLM 只拿到事实做「改写」，提示词明确禁止新增数据；调用失败自动用规则文案。更进一步，规则会给出 `must_mention` 清单（节假日人流、高峰、降水、极端温度等），模型遗漏任意一项，这次润色直接判为不合格并回退——避免「模型漏掉了春节人多」这类问题。

**代价**：文案不如纯生成灵活，偶尔会因为漏关键词被拒。**收益**：可解释、可测试、可离线、成本可控。

### ② 数据结构驱动 UI：新增模式零前端改动

`GET /api/modes` 返回每个模式的 `options` 声明（type / default / choices），前端据此动态渲染时间、下拉、数字、多选控件。新增一种出行场景 = 写一个 `Mode` 子类 + 在 `modes/__init__.py` 加一行 import。

**代价**：选项能力受限于四种控件类型。**收益**：扩展成本极低，接口和前端契约稳定。

### ③ 三级降级，接口永不因外部依赖失败

- 天气：预报 → 气候常年值（并标明 `source: forecast/climate`）
- 语言：LLM → 规则文案（`polish.used=false`，错误写进 `polish.error`）
- 假期：官方安排 → 固定日期估算（`estimated: true`）

### ④ 评分可解释：扣分项与文案同源

评分由同一批规则算出（降水、极端温度、高峰、假期人流），headline 与 score 不会自相矛盾。测试里有「高峰比平峰分数低」「室内比户外在严寒下分数高」这类单调性断言。

### ⑤ 公有云成本保护

公开部署后，每次点击都会消耗天气和 LLM 额度，所以默认：

- 按 IP 限流 30 次/分钟，超限 429 + `Retry-After`
- 相同输入缓存 300 秒
- `TRAVEL_ADVISOR_LLM_ENABLED=0` 可整体关闭大模型
- 密钥只在服务端环境变量，前端和仓库都不出现

### ⑥ 数据诚实性

气候值、节气、估算假期都会在响应里标注，并附 `warnings` 和 `disclaimer`。不把估算包装成预报——这比「看起来更准」更重要。

## 7. 数据与准确性策略

- **法定节假日**：2026/2027 直接用国务院办公厅通知原文（含调休上班日），可追溯到来源链接；
- **气候**：1991—2020 常年值（近似取整），明确标注「非预报」；
- **节气**：世纪常数公式，误差约 ±1 天；
- **限行**：只做概括提示，不编造尾号轮换；
- **未收录城市**：温带季风兜底，并在 `warnings` 说明。

## 8. 演示脚本（5 个场景，按顺序讲）

1. **日常通勤**：上海、明天、通勤
   → 看「天气来源」「早高峰」标签和提前出门建议，说明规则如何扣分。
2. **节假日旅游**：北京、2027-02-06、旅游
   → 假期第 2/9 天、人流高峰、预约提醒，说明节假日数据的来源。
3. **极端天气健身**：白山、2027-01-10、健身
   → 户外跑步 72 分 vs 健身房 90 分，讲「室内/户外分流」的规则设计。
4. **边界兜底**：城市输入「火星」
   → 返回兜底建议 + `warnings`，说明降级策略。
5. **接口层面**：打开 `/api/modes` 和一次 `/api/advice` 的 JSON
   → 说明前端由 options 驱动、响应字段如何支撑可解释性。

## 9. 常见追问与回答

**Q：为什么不全用大模型？**
A：三类问题——事实不可核验（会编天气/限行）、成本与延迟不可控、结果不可复现。规则引擎负责事实，模型负责表达，是我认为更稳的分工。

**Q：怎么保证天气/节假日准确？**
A：能拿到官方来源的用官方（节假日），拿不到的就明确标注估算（气候、节气），并暴露 `source` 与 `estimated`。不假装精确。

**Q：新增一个模式要改多少东西？**
A：一个文件 + 一行 import；前端自动出现按钮和选项。测试补 2—3 个用例即可。

**Q：怎么防止别人刷爆你的 Key？**
A：限流 + 缓存 + 可一键关闭 LLM + 密钥只在服务端；线上再配各平台的用量上限。

**Q：最大的取舍是什么？**
A：默认用气候常年值保证「永远可用」，配置后才接实时预报。准确性与可用性之间，我选了先保证可用，再把准确性做成可选项。

**Q：如果流量大 100 倍？**
A：缓存换 Redis、限流下沉到网关、城市/节假日数据进 DB、天气按城市批量预热、LLM 润色改异步或模板化。

**Q：测试怎么写的？**
A：重点测边界和降级——调休日、单日假期、估算年份、无 Key、坏 Host、超窗日期、限流；另外用单调性断言保证「雨天分数更低」这类业务规则不被改坏。

**Q：「agent」体现在哪？**
A：诚实说：这是「领域规则引擎 + 可选 LLM 的表达层」，不是自主规划型 agent。如果要做成真 agent，下一步是 function calling：把天气、POI、路线作为工具，让模型决定调用顺序，规则引擎退化为工具之一。

## 10. 局限与下一步

- 天气是常年值或 7 天预报，不能当长期预测；
- 限行只给提示，未接交管实时数据；
- 城市数据 31 个，覆盖有限；
- 评分是经验权重，未经交通数据校准；
- 下一步：接实时路况与 POI、把「润色」升级为工具调用、用真实出行数据校准权重。
